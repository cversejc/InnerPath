# 一期模块边界与开发约定

## 架构方向

项目采用模块化单体。前后端按业务领域组织代码，部署和数据存储保持现状；只有出现明确的独立扩缩容、发布或团队边界时，再评估服务拆分。

当前前端已采用领域优先目录；后端保留技术入口与基础设施分层，并将跨越多层的业务核心按领域聚合。Reports、Auth、Users、Audit、Calendar 和 Service Requests 已形成领域模块；User 仍作为共享 ORM 实体，跨领域交付由 application 编排，HTTP 与 Celery 入口留在适配层。

一期核心流程是账号与权限、个人报告、决策日历、服务申请与交付、AI 任务和运营管理。服务介绍、用户直接预约和课程展示与学习不进入一期；相关功能实现已移除。

咨询师读取用户报告、报告任务和日历的授权只依据服务申请分配：分配给当前咨询师且状态不是 `withdrawn` 或 `rejected` 的申请才授予访问权。旧预约及课程 API、后台能力、运行时模型已移除；Alembic 前向迁移 `008` 删除相关表。服务申请是当前交付工作流，与已移除的旧预约模块分离。

## 业务领域

| 领域 | 所有者 | 边界 |
|---|---|---|
| Auth | 认证、角色、邀请、会话 | 身份验证和会话生命周期，不承载报告或日历规则 |
| Users | 用户资料契约、资料校验和更新用例 | 用户资料规则；共享 User ORM 实体仍在 `models/user.py` |
| Reports | 报告读取、历史报告、报告任务 | 报告内容与任务生命周期 |
| Decision Calendar | 用户日历、日历申请、行动与决策记录 | 日历内容、发布状态和用户记录 |
| Service Requests | 用户申请、咨询师分配、AI 初稿、审校和交付 | 当前报告与日历的工作流和授权关系 |
| Audit | 业务审计事件、脱敏和写入接口 | 调用方沿用当前业务事务记录审计事件 |
| Admin | 运营视图、管理端用户操作和导出 | 组合领域能力，不重复实现领域规则 |
| Platform | 数据库、缓存、AI、任务队列、日志 | 跨领域技术能力，不依赖具体页面或路由 |

## 依赖方向

前端页面依赖本领域 API 模块；本领域 API 模块依赖共享 `apiClient`。页面不直接拼接业务 URL，也不从通用业务服务文件导入跨域函数。路由页面组件使用动态 `import()` 按需加载；路由表保留 URL、权限元数据和守卫，不静态导入全部页面。

后端目标依赖方向为 API 路由 -> application 用例（跨域编排或协调异步任务时）-> 领域服务/仓储；简单的单领域查询可由路由直接调用领域服务。路由负责参数、身份和 HTTP 状态码；application 负责编排用例与事务；领域服务负责本域规则和授权；模型负责持久化结构。需要派发异步任务时，由外层适配器将 `tasks/` 中的调度函数注入 application 用例；Celery worker 入口留在 `tasks/`。HTTP 请求元数据在 `api/` 适配层转换为 AuditContext，application 与领域模块不接收 FastAPI Request。领域模块不得反向依赖 API、application 或任务入口。管理后台可以编排多个领域服务，不能成为领域规则的第二份实现。

跨领域访问通过明确的函数或查询接口完成。避免页面之间互相导入、领域服务之间循环导入，以及把数据库查询散落到无关领域。

## 目录归属

前端约定：

| 路径 | 放置内容 |
|---|---|
| `src/views/` | 路由页面的视图组合；页面逻辑和样式较复杂时委托给对应领域目录 |
| `src/features/<domain>/` | 领域 API、页面编排、状态/方法、展示模型、领域组件和领域样式 |
| `src/components/` | 跨领域复用组件；只在单一领域使用的组件留在该领域的 `components/` |
| `src/utils/` | 确实跨领域的纯工具或基础设施；不放置业务 API 聚合服务 |
| `src/styles/` | 全站基础、布局和通用控件样式；页面局部样式归页面或领域所有 |

后端当前采用技术分层目录，新增代码按以下方式归属，并保持同一业务的文件使用一致前缀：

| 路径 | 放置内容 |
|---|---|
| `backend/app/api/v1/` | HTTP 路由和资源路由聚合；复杂资源按职责拆路由文件 |
| `backend/app/application/` | 跨领域用例、事务和流程编排；不放 HTTP 路由或 Celery 入口 |
| `backend/app/domains/<domain>/` | 跨层的领域核心：该领域的持久化模型、契约和用例服务；仅当一个领域已有多组相关模块时采用 |
| `backend/app/domains/audit/` | 业务审计事件模型、脱敏和写入接口；调用方沿用当前业务事务，不自行提交审计记录 |
| `backend/app/domains/users/` | 用户资料契约、资料校验和资料更新用例；共享用户 ORM 实体仍由 `backend/app/models/user.py` 提供 |
| `backend/app/schemas/` | 没有单一领域所有者的共享请求、响应和数据交换结构；领域专属契约放在对应 `domains/<domain>/` |
| `backend/app/services/` | 共享技术/平台服务及尚未成组迁入领域包的业务用例；同域模块使用稳定领域前缀 |
| `backend/app/models/` | 被多个领域直接共享的 SQLAlchemy 实体；领域专属模型放在对应 `domains/<domain>/` |
| `backend/app/core/`、`db/` | 跨领域技术能力、数据库连接与会话 |
| `backend/app/tasks/` | 异步任务入口和任务编排 |

当某个后端领域已有多组路由、服务和契约，且跨域改动频繁时，可将模型、契约和用例服务成组迁入 `app/domains/<domain>/`。HTTP 路由继续由 `api/v1` 暴露，Celery 等基础设施入口继续由 `tasks/` 装配；领域代码不得反向依赖这些入口。避免只为目录形式统一而批量移动稳定代码。迁移时明确导入边界，并同步调整该领域测试。

## 技术栈与共享实现

依赖版本以仓库清单为准：前端使用 Vue 3、Vue Router、Vite、Axios 和 Vant 4；后端使用 FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Redis 与 Celery。移动端表单和交互控件优先使用 Vant；不再引入承担同类职责的第二套 UI 库。

复用约定：

- HTTP 请求统一通过 `src/utils/apiClient.js`；领域 endpoint 放在对应的 `src/features/<domain>/api.js`。
- 全站导航、页脚和图标分别复用 `BrandNav`、`BrandFooter`、`IconMark`；移动导航由 `BrandNavMobileMenu` 承担。
- 测评和用户中心的档案字段/摘要优先复用 `ProfileFields`、`ProfileSummary`；领域专用展示组件不提升为全局组件。
- 通用色彩、字体、间距、按钮和表单规范以 `design-system/innerseek/MASTER.md` 与 `src/styles/` 为准；新增全局样式应落在对应基础、布局或控件文件中。
- 移动端通用交互优先复用 Vant 4 控件；按组件引入并配套引入该组件样式，禁止无差别全局注册整套组件。Vant 主题变量统一映射在 `src/styles/vant.css`，使用项目设计 token；品牌导航、档案摘要等组合组件仍由项目组件负责。表单字段应保留实际输入控件上的标签和错误关联语义；控件库无法承载时沿用项目原生控件与共享样式。
- 普通用户端和跨端工作流的主要操作按钮优先使用 Vant Button，并复用 `src/styles/components.css` 的项目按钮样式。运营台与咨询师工作台的高密度列表行操作可保留原生按钮；日历日期/阶段选择、ARIA 标签页和需要自定义键盘焦点管理的控件保留领域专用原生实现。同一操作组保持一致。
- 提取共享组件或工具前先搜索现有实现；只把跨页面/领域的稳定能力放入共享目录，避免产生只转发一次的包装层。

## 文件职责约定

- 一个页面或组件聚焦一段用户流程；复杂状态放进同领域 composable，重复展示放进子组件。
- API 模块只封装 HTTP 请求和响应，不承载视图状态或业务决策。
- Python 路由模块按资源域拆分；每个服务模块围绕一类业务能力组织。
- 单文件接近 400 行，或开始同时承担两个以上领域职责时，应评估是否按自然边界拆分；紧密耦合的单一算法或组件不为行数而拆。
- 拆分时保持既有 URL、响应结构和业务行为；需要变更契约时单独说明并迁移。
- Alembic 已发布迁移保持不可变。表结构清理只通过新的前向迁移完成。
- 前端纯逻辑测试使用 Node 内置 `node:test`（`node --test`），生产构建使用 `npm run build`。后端完整测试从 `backend/` 目录运行 `python -m pytest`，以应用 `backend/pytest.ini` 的测试范围；`backend/test_ai_service.py` 是手动 AI 联调脚本，不属于自动测试集。测试文件靠近对应领域或使用 `backend/tests/` 的既有组织方式。

## Vant 4 分支吸收结论

`codex/vant4-mobile` 的独有提交 `a41537f`、`bacfab9` 已完成逐项对照，不整支合入当前架构分支。前者全局注册了多组 Vant 组件并在 `App.vue` 另设一套主题值；当前实现改为组件内局部导入，并在 `src/styles/vant.css` 将 Vant 变量映射到设计 token，避免重复主题来源和无用全局注册。后者基于尚未完成页面拆分的旧视图，并保留已退出一期的预约、课程等页面；当前分支已在领域组件中逐项采用其有效的 Vant 交互，不覆盖新的路由、状态和 API 边界。

普通用户端的认证、测评、服务申请、个人空间、报告、日历、档案和移动导航操作已使用 Vant 控件；移动导航使用 ActionSheet 和 Tabbar。咨询师工作台的主要流程按钮，以及管理台用户运营、报告、任务、日志、日历编辑、日历申请审核、成员邀请和详情抽屉的主要命令也使用 Vant Button；管理台密集表格行操作、筛选/状态选择、抽屉标签与列表行、咨询师工作台的 ARIA 范围标签和申请选择行、日历日期/阶段选择及菜单遮罩触发器继续使用原生控件并保持各自语义。移动端输入和确认弹窗优先使用 Vant Dialog、Field、Button。后续从旧分支吸收 UI 改动时，只移植经核对的单项控件或样式，不合并旧页面快照。
