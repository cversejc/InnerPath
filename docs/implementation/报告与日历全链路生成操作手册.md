# 报告与日历全链路生成操作手册

本文记录服务申请 #12 在服务器上第一次完整走通“报告六节点审核 → 交付 → 30 天日历生成 → 发布校验”的操作路径，并整理成可复用脚本。脚本在容器内运行，业务写入全部走公开 HTTP API，数据库只用于只读诊断。

## 适用前提

- 目标环境是服务器上的服务，不是本地数据库。生产部署：`root@47.82.81.147`，后端容器 `innerpath-backend`。
- 服务申请已由用户提交；对话过程中的报告申请按“服务申请 → 报告案例 → 报告结果”串联，日历只接受当前用户已交付的报告。
- 管理员账号 `id=1` 可用；需要两名咨询师席位（命理、心理）的账号 id。
- 模型网关已配置默认 provider；需要切换或核对时使用工具中的 `probe-gateway` / `configure-model` / `switch-provider`。
- 时区固定 `Asia/Shanghai`；日历范围不超过 60 天，本次为 30 天。

## 工具

| 文件 | 用途 |
| --- | --- |
| `backend/tools/report_calendar_operator.py` | 唯一的操作入口：状态、指派、S1–S6 审核、交付、日历生成/重试/校验 |
| `backend/tools/diag_calendar_runs.py` | 只读诊断：列出某个日历申请的全部技能运行与错误、按运行 id 展开逐日输出 |
| `backend/tools/validate_calendar_days.py` | 离线校验：对 `/calendar/me` 的 JSON 转储检查日覆盖、窗口、觉察、语气与行动引用 |

部署与调用（在仓库根目录使用 PowerShell）：

```powershell
docker cp backend/tools/report_calendar_operator.py innerpath-backend:/tmp/
docker exec innerpath-backend python /tmp/report_calendar_operator.py status --service-request-id 12
```

脚本在内存中为用户生成访问令牌，不落盘；只把幂等键与进度写入状态文件（默认容器内 `/tmp/innerpath-report-calendar-state.json`，可用 `--state-path` 指定）。容器重建后状态文件会丢失，重跑同一申请时建议继续使用同一路径以复用幂等键。

## 标准流程

| 阶段 | 命令 | 说明 |
| --- | --- | --- |
| 1. 状态 | `status --service-request-id 12` | 打印服务申请、报告案例与 S1–S6 工作区摘要、检查状态与开放问题 |
| 2. 指派 | `assign --service-request-id 12 --mingli-consultant-id A --psychology-consultant-id B` | 分别指派命理与心理席位，可只传一边 |
| 3. 报告 | `run-report --service-request-id 12 --birth-place "山西省晋中市"` | 依次完成 S1–S5 并执行 S6 交付，每一步幂等 |
| 4. 日历 | `calendar-generate --service-request-id 12 --start-date 2026-10-10 --end-date 2026-11-08 --goal "围绕当前学业困扰，找到认识自己、明确方向并稳定行动节奏的路径。"` | 以交付报告为来源创建日历申请并轮询到 `fulfilled` |
| 5. 校验 | `calendar-verify --user-id 5 --calendar-id 2` | 校验天数、缺失、重复与空日；`ok: true` 即通过 |

分步执行时把第 3 步换成 `s1`、`s2`、`s3`、`s4`、`s5`、`finalize`，便于在节点之间人工查看。`s6-once` 只跑到最新一次最终检查；`s6-check --check-label <标签>` 可在修订后重新排队检查。

S6 需要人工修订报告片段时使用 `s6-dump --out-path` 导出当前片段、`s6-plan --out-path` 导出已确认的内容计划，然后准备“fragment_key → 新正文”的 JSON 计划执行 `s6-revise --plan-path`（只替换正文）或 `s6-coverage --plan-path`（只重挂需求覆盖，不改正文），最后 `s6-check` 与 `finalize`。

S1 分析因输出超长被截断时，先 `rerun-s1-analysis`（用压缩输出指令重新排队分析草稿），再执行 `s1` 让程序物化并检查新草稿。

## 日历请求载荷

`calendar-generate` 按下列字段组装请求，未传的可选字段用默认值：

| 字段 | 本次取值 | 说明 |
| --- | --- | --- |
| `profile_version` | `3` | 日历配置版本，脚本固定 |
| `source_report_id` | 服务申请 `result_id`（报告结果 id，本次为 9） | 必须属于当前用户且已交付 |
| `start_date` / `end_date` | `2026-10-10` / `2026-11-08` | 含首尾共 30 天，跨度不超过 60 天 |
| `focus_topics` | `career,self,finance` | 逗号分隔，可省略 |
| `usage_scenario` | `morning_planning` | 可省略 |
| `expected_outcomes` | `action_windows,daily_prompt,decision_review,reflection` | 逗号分隔，可省略 |
| `available_minutes_per_day` | `30` | 可省略 |
| `goal` | 围绕当前学业困扰…… | 必填 |
| `decision_description` / `additional_info` | 未使用 | 可选补充 |

生成期间脚本按 `generation_stage` 轮询并打印进度；超时用 `--poll-timeout` 调整（默认 2400 秒）。失败时申请状态为 `failed` 并可读 `generation_error`，使用 `calendar-retry --service-request-id 12 --request-id <日历申请 id>` 重试；失败任务不产生可见日历。

## 本次发现并修复的真实缺陷

| 缺陷 | 症状 | 修复 |
| --- | --- | --- |
| 日方向修复缺约束 | 逐日 `suitable` 少于 2 条时报 `calendar_directions_invalid`，修复指令只要求“修复来源错误”，模型把被点名的条目删掉，条数越修越少，批次反复失败 | 错误详情携带 `entry_date`、`suitable_count`、`expected_range`；修复指令硬性要求保留 2–3 条非空条目，被点名引用未排入练习的条目改写成不调用报告 Action 的日常安排 |
| 校验意见原文定位失败 | 六节点审核中 AI 意见的 `evidence` 不能逐字命中目标片段时，`final_qa_source_quote_invalid` 直接让运行失败 | 先尝试从证据中恢复最长连续原文摘录；恢复不到则降级为 `VALIDATOR_EVIDENCE_UNVERIFIED`（MINOR，人工复核），不再硬失败。整体质量运行同时携带 `node_activation_no`，指令强调单一连续原文子串 |
| 最终校验对账过早返回 | `REPORT_QA` 运行完成后命中负责人守卫提前返回，CHECK 停留在 `RUNNING`，`step.last_error` 残留旧错误 | `REPORT_QA` 的结果先对账（CHECK 置 `COMPLETED`/`STALE`）并清空 `last_error`，再走负责人守卫 |
| 节点审核迁移不可圈定 | 迁移工具只能全量处理活跃案例，且总会自动准备第一步，无法“只迁指定案例、先停车” | 增加 `--case-id`（可重复）与 `--no-auto-prepare`，迁移记录包含 `auto_prepare` |

## 生成后校验清单

1. `status` 显示服务申请 `result_type=report`、`result_id` 非空，报告案例为交付态。
2. `calendar-verify --user-id <用户> --calendar-id <日历>` 输出 `ok: true`，`expected_days == actual_days`，`missing`、`unexpected`、`empty_days` 均为空。
3. 需要更细的离线检查时：`get-json --user-id <用户> --path /calendar/me > /tmp/calendar.json`，再运行 `py -3.11 backend/tools/validate_calendar_days.py /tmp/calendar.json`，确认每天都有至少 2 个窗口，且 `energy_awareness`、`tone_explanation`、`action_refs` 非空。
4. 日历申请状态为 `fulfilled` 且带 `calendar_id`；用户端 `/calendar/me` 返回同一天数。
5. 卡住或反复失败时用 `diag_calendar_runs --request-id <申请>` 查看该申请的全部技能运行、`calendar_directions_invalid` 等错误详情，再决定修复或重试。

## 幂等与边界

- 操作脚本为每类写入生成带指纹与尝试序号的幂等键，保存在状态文件；重跑已完成的节点或日历申请不会重复写入。
- 已交付报告与已发布日历不重跑；只有用户提出新需求时才创建新的日历申请。
- 生产环境的写操作全部通过公开 API；数据库连接只用于 `diag_calendar_runs.py` 的只读查询。
- `configure-model` 从标准输入读取包含 `api_key` 的 JSON，错误信息会先脱敏再输出；密钥不写入仓库、脚本或状态文件。
- 日历生成是长任务（本次 30 天固定 8 次技能调用，另可能包含格式修复），`run-report` 与 `calendar-generate` 需要保持终端会话直到打印最终状态。

## 临时产物清理

每次跑通后先完成“生成后校验清单”，并确认缺陷修复已合并、部署版本与仓库 HEAD 一致（可比对容器内 `app/` 下修补文件的 sha256），再清理本次运行的临时副本；不要带着未合并的临时文件收工。清理前先确认没有正在排队或运行的报告、日历申请。

- 容器 `/tmp`（`docker exec innerpath-backend ls -la /tmp`）：`report_calendar_operator.py`、`_diag_calendar_run.py`、`_validate_calendar_days.py`、`innerpath-report-calendar-state.json`、`s6-dump.json`、`s6-plan.json`、`calendar.json`、`production.py.bak`、`report_quality.before-activation-fix.py` 等运行期副本与导出。
- 服务器宿主机 `/tmp`：上传用的部署脚本副本（`deploy-*.py`、`innerpath-*.py`）、`case12-*.json` 导出，以及同样的一次性脚本。
- 本地仓库：`__pycache__`、`.pytest_cache`、导出到临时目录的 `calendar.json`/`s6-*.json`。

```powershell
# 本地：列出将被清理的缓存项，确认后再删除
git status --ignored=matching --porcelain=v1 | Select-String '__pycache__/|\.pytest_cache/'

# 服务器：先盘点再按显式文件名删除
ssh root@47.82.81.147 'ls -la /tmp'
ssh root@47.82.81.147 'docker exec innerpath-backend ls -la /tmp'
ssh root@47.82.81.147 'docker exec innerpath-backend rm -f /tmp/report_calendar_operator.py /tmp/innerpath-report-calendar-state.json /tmp/calendar.json'
```

保留项：`.env`（含密钥）、`backend/.venv`、`node_modules`、`/opt/innerpath/current` 部署目录、`logs/` 运行日志与数据库数据；`/tmp` 下的系统 socket 与 `systemd-private-*` 目录不属于产物。默认状态文件在容器 `/tmp/innerpath-report-calendar-state.json`，删除后同一服务申请重跑会生成新的幂等键，只有确认该申请不再复跑时才删除。清理完成后用 `docker ps` 与 `git status --short --branch` 复核：容器 `healthy`、工作区干净即收工。
