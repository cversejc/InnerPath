# 产品分析框架到报告的映射契约

维护日期：2026-10-04。产品内容基线为[产品分析框架](产品分析框架.md)；生产架构与报告编排负责实现这些内容要求，不得静默删除核心内容。

当前契约版本：`product-analysis-2026-10-04-v2`。共38项内部分析、16项报告内容职责及4项全文规则。权威定义在 `backend/app/domains/content/product_framework.py`，内容验证在 `framework_coverage.py`；本表与该版本对应。

## 契约的工作方式

框架要求 → 逐项分析与证据 → 人工确认的判断/分析 → 主线与内容分配 → 有来源的正文 → 独立逐项校准 → 人工终审与冻结版本。

- 新建 `report.production` 案例将完整契约与摘要固定在申请快照中；既有案例不自动升级，已交付报告不重新生成。
- 分析片段的覆盖说明保存在 `source_snapshot.framework_coverage`，正文片段的覆盖说明保存在 `source_snapshot.requirement_coverage`。均随不可变Revision保存。
- `NarrativePlan.plan_json`及其`content_plan.framework`保存契约；逐段输入携带该段要求、检查条件和对应来源；最终QA及交付版本保存独立审核记录。
- 小标题可个性化。表中的片段键是内部内容职责，不能作为读者标题；覆盖指的是实际表达，不是标题存在或引用数量。

## 全文规则

- `P.narrative`：三章首页关键句与概览路径；一条暗线，理解→整合→行动，避免重复完整解释。
- `P.style`：第二人称、现实语言；按明确阅读偏好调节，不改变事实；避免模板、空泛安慰和术语堆叠。
- `P.fidelity`：只消费已确认来源，不新增经历、心理判断或行动；问卷反馈校正符号解释。
- `P.safety`：无诊断、无单信号强人格结论、无必然未来；保留多系统冲突及用户主体性。

## 覆盖状态与证据不足

| 状态 | 含义 | 放行要求 |
| --- | --- | --- |
| `FULFILLED` | 依据充分，内容已完成 | 有理由和对应正文逐字摘录，独立审核确认实质满足检查条件 |
| `DEFERRED` | 已明确说明缺失资料与暂缓范围 | 正文中可见暂缓说明，必须有补充问题；不虚构内容 |
| `NOT_APPLICABLE` | 该内部分析在当前资料下不适用 | 仅允许内部分析使用，须有解释和片段摘录；核心报告职责不能如此省略 |
| `MISSING` | 尚未形成可接受产物 | 阻断节点或交付；须修订来源/正文并重新审核 |

没有覆盖记录不是默认完成。若关键BLOCK或ACTION不足，当前完整报告门禁阻断，要求补充资料与上游分析；不自动拼出卡点或实验凑数。

记录格式示例：

```json
{
  "requirement_id": "R.self_belief",
  "status": "DEFERRED",
  "reason": "用户尚未提供面对权威期待时的具体感受",
  "quote": "关于你内心的应该与必须，目前仍需要一个具体事件来核对。",
  "follow_up_questions": ["最近一次你想表达不同意见时，发生了什么？"]
}
```

内部分析记录使用相同状态/理由/摘录/补问字段，requirement_id通过稳定analysis key确定；最终独立审核另加fragment_keys，必须覆盖该要求的所有正文归属。

## 确定性门禁与语义门禁

1. S1–S4：38项必须逐项人工确认；新案例还检查每项覆盖状态、摘录与补问。MISSING或无覆盖记录不能完成节点。
2. 开始写作：所有MUST_INCLUDE（含低重要度）与主线指定项取并集；核心报告职责必须分配且标为必需；当前确认依据与契约版本必须匹配。
3. 行动：必须3–5项；block_refs只可指向已确认BLOCK；每个选定卡点须被行动回应。卡点为3–5项，最终优先4–5；内容上的证据不足理由由独立QA再核对。
4. 逐段写作：只读分配来源；全部分配的分析/行动需纳入来源记录。各内容职责需有覆盖记录，摘录必须实际存在于当前正文。
5. 最终QA：先运行程序门禁，再由独立Validator逐项返回16项framework_review；不以作者声明或七维总分代替内容校验。MISSING生成BLOCK。
6. 交付：绑定当前正文指纹；即使把BLOCK标为已处理，独立review仍为MISSING也不能放行；必须补齐正文、重新校准并由人工终审。

程序验证结构、状态、引用、文本摘录和版本；是否有心理洞察、推导是否成立、暂缓理由是否合理，由独立语义校准与咨询师判断。

## API与持久化

- 创建/修订分析片段时可通过已有内容Revision API提交framework_coverage。创建/修订正文时提交requirement_coverage。表达修改沿用已有覆盖说明，若原摘录被移除则必须更新覆盖记录并重新校准。
- 分析完成响应增加framework_coverage_issues；编排保存framework.allocations；质量响应的latest_validator_run增加framework_review。没有新增表或数据库迁移。
- 语义投影保留relation_refs供编排/写作使用，不能凭关系ID创造新结论。
- 已审核历史案例沿用原快照；MUST_INCLUDE漏项及Action角色错误作为通用正确性修复适用于重新运行的流程。
