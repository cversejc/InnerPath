# 产品分析框架覆盖核查与缺口清单

核查日期：2026-10-04。范围：三份设计文档、当前报告生产代码、青鸟验收成果及相关自动测试。本次只形成分析文档，不修改应用、数据库或已交付报告。

## 结论

现有系统已经实现以《产品分析框架》为来源的 S1–S6 生产链，不能再用“尚无 Workflow、Finding、NarrativePlan、QA”的旧差距结论描述现状。

但尚不能认定“完整覆盖，且每次都能生成符合框架的报告”。当前完成度主要体现在流程、分析条目、版本记录和来源关联；框架要求的语义内容、推导关系及最终阅读结构，仍有依赖提示词和人工补救的部分。

最需要补的是：**将《产品分析框架》转成版本化的分析与报告内容契约，按内容职责验证覆盖，而不只按片段数量和引用 ID 判定完整。**

后续落地：已建立[产品分析框架到报告的映射契约](产品分析框架到报告的映射契约.md)，接入新案例的分析覆盖、报告内容分配、正文覆盖、独立逐项审核和交付门禁，同时修复MUST_INCLUDE漏分配与ACTION错指非BLOCK的问题。下文保留本次核查时的原始缺口；技能版本固定、局部STALE和日历结构化投影已由后续批次补齐，差异化案例的真实模型验收仍需独立处理。

第二批落地：[结构化分析推导链与验收](结构化分析推导链与验收.md)接入了工作流/案例技能固定、八项结构化分析及资源到行动的来源链；新增真实模型合成案例验收工具与记录。下文P0/P1条目继续保留核查时的背景，不能用它们判断这些新实现尚未开始。结构完整不等于专业判断准确，仍需独立语义审核和真实客户验收。

## 需要优先补齐的缺口

### P0-1：产品内容要求没有形成最终报告的完整契约

`report_content_plan.py:296` 只有匹配到 `SELF_BELIEF / SELF_PERCEPTION / IDENTITY` Finding 才创建 `self_perception`，而且 `required=False`。整体心灵结构、能量、关系、自性方向、阶段地图、结尾也有可选配置。

`report_sop_plan.py:4` 把权威分析分给 `self_perception`，但并不保证这个目标存在。复现中，38项分析齐全，权威分析最终被通用来源重叠规则分到 `outer_self`，编排校验仍通过。

青鸟16段验收稿没有单独的 `self_perception`。其首页主要呈现阅读路径，尚未明确组织产品要求的“向世界展示的我 → 以为的自己 → 潜意识层面的自己 → 自性”结构。已有自述不等于已完成这一层剖析。

**补齐方式：**为核心内容建立 requirement ID、完成条件和缺失处理。可以合并小节或调整标题，但必须明确这些内容在哪段完成、依据是什么、哪些暂缓。不要强制每份报告有相同小标题。

### P0-2：MUST_INCLUDE 存在漏项路径

`report_content_plan.py:200` 和 `:740` 以 NarrativePlan 的 `must_include_findings` 为门禁集合，没有与所有 `reportability=MUST_INCLUDE` 的已确认 Finding 取并集。

排序提高了这类 Finding 的优先级，但排序不能保证全部分配。使用4条低重要度、MUST_INCLUDE、非通用角色 Finding 的最小案例，复现1条没有任何分配，而 `validate_report_content_plan` 返回空问题列表。

**补齐方式：**程序将来源资产的 MUST_INCLUDE 与主线指定项合并，检查实际已确认正文覆盖；如果人工决定排除，应回到上游调整 reportability 并记录理由。

### P0-3：卡点到行动的完整推导链没有被强校验

`runtime.py:583` 的 `validate_growth_experiments` 只检查 `block_refs` 指向某个已知 Finding，没有验证目标的语义角色确为 BLOCK。3个 Action 全部指向 PERSONA 的最小案例仍可通过。零 Action 也能通过这个验证函数；后续编排可能阻断，但 S4 本身未形成一致的内容准备门禁。

编排门禁也没有将“最终优先4–5卡点、3–5实验”作为完整报告的统一约束。框架允许证据不足时减少内容，这种例外应明确记录，而不是由通用角色匹配静默决定。

`queries.py` 的写作语义投影保留 claim、role 和 structured_data，但没有单独投影 Finding 的 `relation_refs`。数据库已有关系能力，尚未完整用于写作规划和推导检查。

**补齐方式：**保留并验证 `用神候选/资源 → 调节功能 → 能力 → 现实缺口 → Block/Need → Integration Task → Action` 的关系；检查每个选定卡点被哪些实验回应，而不只检查成长实验片段同时带有一些卡点与行动来源。缺少这条链应返回语义缺口。

### P1-1：分析“有条目”与正文“讲清楚”仍然混在一起

阶段门禁检查38个分析 key 是否确认。编排检查引用是否合法、是否重复分配，尚没有完整检验所有核心要求在正文中是否实质完成。

例如，`analysis.s2.cycle` 已引用，不代表正文完整表达触发、核心情绪、自动想法、防御、短期保护、长期重复。资料不足标注“暂缓”是合理产物，但不应与“已完成分析”混为相同内容状态。

**补齐方式：**增加 `FULFILLED / DEFERRED / NOT_APPLICABLE / MISSING` 等内容覆盖状态、理由和补充问题。程序验证结构，语义Validator核对正文是否真正表达；人工确认例外和专业判断。

### P1-2：个体化整合需要更稳定的结构与来源

青鸟内部S3/S4已写出中式人物意象、用神转译、两端整合；最终破局节主要剩四种能力和象限描述，人物具象化与完整转译链没有充分进入读者内容。

阶段地图已有真实年份和四个栏目，但后续阶段不少仍接近“十神名称 → 通用主题”的映射，没有逐运明确呈现原局互动如何改变本人的议题。八维部分保留探索/价值/执行/反馈四个入口，但没有清楚呈现本人的功能运作路径与张力。

**补齐方式：**将自我信念、核心情结、对立两端、原型及学习资源、用神调节功能、逐运原局互动、能量路径拆成可审核的结构化产物，再按已确认来源表达。不能为了内容完整补造经历或推断MBTI类型。

### P1-3：技能版本没有在所有实际生产入口固定

主架构§5.2要求 WorkflowVersion 绑定具体 SkillVersion。当前单次 SkillRun 已保存实际版本，但 `queue_case_analysis_draft` 获取默认已发布技能；逐段写作和叙事入口也查询最高已发布版本（`skill_runtime.py:371 / :544`）。

这意味着同一Case在跨节点或跨片段执行期间，可能使用后来发布的技能版本。运行记录可以追查，但与“Case绑定的工作流固定整条生产链”仍有差别。

**补齐方式：**在实例创建时固定分析、规划、写作、校准技能版本及框架内容版本。已运行Case升级须有明确操作和影响说明。

### P1-4：来源变更后的失效范围仍过大

`dependencies.py:111` 将 NarrativePlan 标记STALE，随后 `mark_report_fragments_stale_for_plan` 将该主线下全部当前报告片段标记STALE。

所以虽然有来源依赖追踪和局部重生成接口，修改一个上游Finding仍可能让整份报告失效。它不符合编排设计§70–71及验收§76要求的“只让真正受影响片段失效”。

**补齐方式：**区分来源表达、局部语义和主线变化。先评估主线与分配影响；主线未变时，按直接与传递依赖使相关片段失效。主线确实变化时，再比较分配差异，不覆盖旧已审核版本。

### P1-5：报告到日历仍主要是正文传递

`calendar/requests.py` 从兼容Report复制 summary、structured_sections 等；日历生成另走现有模型调用。未见完整的、以冻结ReportVersion为依据的 `practice_rhythm` 与 Action/Block/方向投影契约。

当前能生成30天日历，但不能仅凭日期齐全证明每天的行动真正延续已审核实验。

**补齐方式：**冻结 `daily / weekly / monthly / quarterly` 结构、Action ID、卡点/方向引用和ReportVersion ID；日历保留这些引用并按用户可用时间排程。Calendar仍维持独立流程。

### P2：质量回归与表达知识还需要扩展

目前青鸟完整验收很有价值，但生日和出生城市是明确标注的演示补充，开发审核不能证明对真实客户命盘的专业准确性。单个成功案例也不足以证明跨用户的“形散神不散”。

ReaderProfile已有控制字段，但默认方案以通用值为主，未看到完整的主导/辅助功能阅读规则；《产品分析框架》自身也只留下“16型mbti文字风格参考”的标题，没有实际规则表。金句库当前较小。

**补齐方式：**补充真实信息充分、缺时辰、无MBTI、多系统冲突、自述反证、少卡点、短篇偏好等回归案例；检查问卷替换是否真正改变结论与实验。文风优先采纳明确阅读偏好，类型参考只调表达，不改语义。

## 设计本身需要明确的边界

1. 产品框架SOP图将命理组/心理组审核分工画得很具体；当前主要沿用咨询师分配与步骤权限。需要确定是否要求分组、分能力或交叉终审，不能只凭六个节点认定组织职责全部落地。
2. SOP图表现为报告后生成30天日历；主架构§16明确用户主动请求、独立Calendar流程。当前实现采用后者。应同步产品图，明确日历是默认附带还是主动生成。
3. 框架§4.2为3–5卡点，§5.4最终呈现优先4–5；编排又允许动态省略非必需片段。需要定义标准完整报告与证据不足报告的内容门槛及例外记录。
4. 旧自助 `POST /reports` 已标deprecated，但仍可走旧生成任务，绕过Case六步审核。新服务申请已接Case。若要声明“产品所有报告都基于该框架”，还需明确旧入口的开放范围、最终退出或统一策略。
5. 框架部分符号映射含强诊断式示例，其§5.5又禁止诊断和单信号强结论。当前技能使用条件化探索语言是合理的边界处理，应把这种改写规则同步到维护规范。

## 建议的补齐顺序与验收标准

### 第一批：先保证不会漏和错配

- 建立框架要求 → 分析产物 → 已确认判断 → 报告内容职责的映射契约。
- 保证意识自我等核心内容有明确归属或暂缓记录。
- 合并所有MUST_INCLUDE，修正Action对BLOCK的角色校验。
- 对核心内容缺失、必须判断漏项、行动错误引用建立失败验收。

### 第二批：保证推导足够深且可追查

- 结构化情结链、对立两端、原型学习资源、用神调节功能、阶段互动和能量路径。
- 将语义关系完整投影给Planner/Allocator，验证Block → 需要发展的能力 → 工具 → 实验。
- 分别检查“内部分析完整”和“用户报告已表达”，而不要求把所有内部分析原文搬进报告。

### 第三批：保证变化和下游行为符合设计

- 固定实例所用框架与技能版本。
- 上游变化按真正依赖局部失效，旧版本保持可追溯。
- 冻结实践节奏，日历消费已交付版本的结构化实验。
- 用多个差异明显的用户案例验证内容、叙事和行动的个性化。

最终验收应同时回答：**分析完整了吗？核心结论有现实依据吗？推导链成立吗？报告真正表达了吗？行动承接了吗？修改后哪些内容须重审？**
