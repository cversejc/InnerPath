# 功能模块独立性评估与清理决策

> 本文记录清理前的模块评估及最终决策。当前开发规范以[一期模块边界与开发约定](architecture/一期模块边界与开发约定.md)为准。

## 当前产品范围

产品尚未发布，已确认无需保留预约、课程等旧功能的数据或兼容实现。服务介绍、用户直接预约、课程展示与学习的前端页面、路由、API、后台能力和运行时模型均已移除；Alembic 前向迁移 `008` 删除对应数据库表，既有迁移文件保持不变。

服务申请是当前报告和日历的工作流，包含用户提交、工作人员分配、AI 初稿、审校与交付。它与已删除的用户预约是不同领域，继续保留。

## 当前领域边界

| 领域 | 主要职责 | 入口 |
|---|---|---|
| Identity / Users | 认证、角色、邀请、会话和用户档案 | `src/features/auth/`、`src/features/users/`；`backend/app/api/v1/auth.py`、`users.py` |
| Reports | 报告读取、报告任务和报告展示 | `src/features/reports/`；`backend/app/api/v1/reports.py`、`report_task_routes.py` |
| Decision Calendar | 日历内容、用户行动记录和日历申请 | `src/features/calendar/`；`backend/app/api/v1/calendar.py` |
| Service Requests | 服务申请、工作人员分配、审校和交付 | `src/features/service-requests/`；`backend/app/api/v1/service_requests.py` 及同域路由 |
| Admin | 运营概览、用户与领域管理、审计和导出 | `src/features/admin/`；`backend/app/api/v1/admin*.py` |
| Platform | 数据库、缓存、短信、AI、异步任务和日志等技术能力 | `backend/app/core/`、`db/`、`tasks/` |

管理端会组合多个领域的数据，但组合逻辑归管理入口负责；各业务规则仍由其所属领域维护。咨询师读取报告、报告任务和日历的授权依据是有效服务申请分配。

## 架构判断

前端按领域组织，路由页面主要负责组合领域页面、组件和样式，领域 API 通过共享 `apiClient` 访问后端。

后端目前按技术层组织目录：路由在 `api/v1/`、契约在 `schemas/`、业务规则在 `services/`、持久化模型在 `models/`。路由和服务文件已用资源名及领域前缀拆分，例如服务申请和管理后台。对当前模块化单体，这种分层组织是合理的；开发新能力时应继续遵守稳定的领域命名与依赖方向。若某个领域继续扩大、跨域改动频繁，再基于具体需求做成组迁移，不需要为了目录形式整体重写后端。

## 清理前评估结论

此前仅隐藏前端入口并不足以关闭预约和课程能力：API、后台与数据模型仍会被访问。因此，最终选择完整移除对应运行时实现，并通过前向迁移清理数据库表；这项决策已完成，不再适用早期“保留兼容能力、等待数据确认”的建议。

未来如重新引入预约或课程，应按新的产品需求重新设计数据模型、接口、权限与模块边界，不恢复已删除的旧实现。
