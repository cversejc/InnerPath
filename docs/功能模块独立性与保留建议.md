# 功能模块独立性评估（清理前）

> 当前决策（2026-10-01）：本文件后续的保留建议形成于清理前，已被产品决策覆盖。产品尚未发布，无需保留预约或课程历史数据；相关页面、API、后台能力和运行时模型已移除，数据库表由 Alembic 前向迁移清理。服务申请与旧预约是不同工作流，服务申请继续保留。

> 更新日期：2026-10-01
> 分析范围：前端路由与页面、前端 API 服务、后端 API 与业务服务、数据库模型与迁移、后台与咨询师工作台

## 一、结论

当前项目的核心用户流程确实主要是“个人报告”和“决策日历”。服务页、课程页、预约页虽然在前端用户流程中被隐藏，但相关代码并没有被真正移除。

这些模块是“局部独立、整体有耦合”：

- 服务页和课程页的前端实现相对独立，保留不会直接影响报告和日历。
- 预约页面已归入暂停模块并按路由动态加载；预约数据和接口仍被管理后台、咨询师工作台的预约管理能力使用，不能据此直接删除。
- 报告、报告任务和日历的咨询师访问授权已改为依据有效服务申请分配。仅有旧预约分配的咨询师不再因此获得这些数据的访问权。
- 后台管理层把报告、日历、预约、课程和审计统计集中在一起，因此相关后端模块并不是完全隔离的。
- 短期保留不会阻塞报告和日历的开发，但会增加构建依赖、接口维护、权限检查和认知成本。

建议：短期保留数据模型和必要的后台兼容能力，同时将服务、预约、课程标记为“暂停开放”；前端和 API 做边界隔离。确认没有生产数据、后台运营需求和外部调用后，再分阶段清理。

## 二、当前隐藏方式

`src/config/launchScope.js` 将 `services`、`booking`、`courses` 设置为关闭，路由守卫在访问这些路由时重定向到首页。当前隐藏机制只发生在前端路由层，并不等同于删除功能或关闭后端接口。

暂停页面位于 `src/features/paused-commerce`，路由通过动态 `import()` 加载；功能关闭时，路由守卫会重定向到首页。旧页面代码仍保留，但不会作为这些路由的静态导入。

后端 `main.py` 仍然注册 `/api/v1/bookings` 和 `/api/v1/courses`。这些接口使用登录用户校验，但没有对应的服务开关，所以登录用户仍可以绕过前端入口直接调用接口。

## 三、模块独立性评估

| 模块 | 前端独立性 | 后端/数据独立性 | 主要连接 | 建议 |
|---|---|---|---|---|
| 服务页 | 高 | 基本没有独立后端 | 页面只负责展示，并跳转到预约和课程 | 可优先归档或移出活动路由 |
| 课程页 | 高 | 中等 | `Course`、`UserCourse` 表；课程 API；后台课程统计和进度编辑 | 前端可先归档，后端按是否有数据决定保留 |
| 预约页 | 中等 | 较低 | `Booking` 表；预约 API；后台和咨询师工作台的预约管理 | 保留兼容能力，确认数据和调用方后再处理 |
| 管理后台 | 低 | 低 | 同时读取报告、日历、预约、课程、审计数据 | 需要按后台业务重新拆分 |
| 咨询师工作台 | 低 | 低 | 服务申请分配控制报告、报告任务和日历访问；预约管理仍读取旧预约 | 权限依据已迁移；旧预约管理能力暂时保留 |

## 四、关键耦合点

### 1. 预约数据仍用于运营管理，但不再授予报告和日历访问权限

此前咨询师查看用户报告、报告任务和日历时，后端会检查分配给该咨询师的旧预约记录。该授权判断现已迁移到服务申请：申请分配给该咨询师且状态不是 `withdrawn` 或 `rejected` 时才允许访问。

只有旧预约分配、没有有效服务申请分配的咨询师将失去上述数据的访问权；如需延续这类历史授权，应先补建对应的服务申请分配。预约 API 和数据库仍为后台与咨询师工作台提供预约管理能力，因此清理前仍需确认生产数据及外部调用。

涉及位置：

- `backend/app/services/calendar_service.py`
- `backend/app/api/v1/reports.py`
- `backend/app/api/v1/staff.py`

当前授权查询集中在 `backend/app/services/service_request_staff.py`，预约管理接口仍由 `backend/app/services/booking_service.py` 提供。

### 2. 管理后台集中依赖所有业务域

管理后台包含总览、用户、预约、日历、报告、日志和后台成员等分区。总览接口会同时统计报告任务、预约状态、已发布日历、行动记录和课程学习数据；用户详情也会同时展示报告、预约、课程、日历和行动记录。

因此，仅删除用户侧页面不会使课程或预约真正独立。修改 `User`、后台统计返回结构或审计逻辑时，也可能同时影响这些模块。

涉及位置：

- `src/views/AdminConsole.vue`
- `backend/app/api/v1/admin.py`
- `src/features/admin/api.js`

### 3. 前端 API 服务已按领域拆分

此前 `src/utils/businessService.js` 混合了多个领域的请求。目前前端 API 已按预约、课程、日历、报告、管理和服务申请拆分到 `src/features/*/api.js`，共享请求仍通过 `src/utils/apiClient.js`。

暂停模块的预约和课程 API 仍需纳入兼容性检查，删除前应确认后台、咨询师工作台和外部调用方不再使用。

### 4. 数据库迁移历史不是按当前产品范围组织的

初始迁移同时创建了报告、预约、课程和用户课程表。Alembic 环境也会加载所有模型。已有迁移不应直接修改；如果未来确实要删除表，应在确认数据和外部依赖后，通过新的前向迁移完成。

如果生产环境已经存在预约或课程数据，直接删除模型或表会造成数据丢失，也可能影响后台审计和历史统计。

## 五、保留这些代码的实际影响

### 不会立即影响的部分

- 当前普通用户导航只暴露报告、日历、关于和个人空间。
- 报告生成和日历使用的核心服务没有直接调用课程页或服务页。
- 服务页和课程页本身基本是展示型组件；课程页没有调用后端 API。
- 前端和后端没有为这些功能引入明显独有的第三方依赖。

### 会增加的成本

1. **构建与加载成本**：暂停页面仍参与生产构建，但通过动态路由形成独立 chunk；功能开关关闭时不会进入初始页面加载。保留它们仍会增加构建产物和恢复开发时的维护范围。
2. **接口与安全边界成本**：前端隐藏不代表后端关闭。预约和课程接口仍在 API 文档和服务进程中，必须继续维护鉴权、参数校验和数据行为。
3. **后台回归成本**：后台总览、用户详情和咨询师工作台仍会依赖预约/课程数据，报告或日历相关改动可能触发跨域回归。
4. **认知成本**：必须区分当前服务申请与旧预约工作流。README 和架构约定现已标明预约、课程属于暂停模块；兼容 API 与后台能力仍需持续维护，直到业务确认清理范围。
5. **数据迁移成本**：未来要彻底删除时，不能只删 Vue 页面，还需要处理 API、业务服务、模型、后台统计、权限判断、测试和数据库迁移。

## 六、推荐处理方案

### 阶段一：当前阶段，保留但冻结

- 保留现有数据库表和迁移历史，避免破坏已有数据。
- 在产品和技术文档中明确服务、预约、课程暂不属于当前用户发布范围。
- 不再向这些模块添加新功能，除非重新确认产品优先级。
- 如果“暂不开放”是业务约束，建议后端增加服务开关或明确返回不可用状态，而不是只依赖前端路由守卫。

### 阶段二：降低对报告和日历的干扰

- 在后台代码中将报表统计按领域拆分，避免一个总览函数直接承担所有模块查询。
- 已将暂停页面移入隔离目录并改为动态导入，前端请求模块也已按领域拆分。
- 已将咨询师报告、报告任务和日历的授权依据迁移到服务申请分配；仅有旧预约分配的历史咨询师需按业务需要补建授权。
- 服务申请 API 已按用户、咨询师、任务和管理员路由拆分；日历申请、报告生成策略和命理基础适配也已归入独立服务模块。
- 全局样式和若干较大的视图样式/脚本已按职责拆分；剩余接近阈值的模块保持单一职责，不为行数做机械拆分。

### 阶段三：确认不再需要后再清理

推荐清理顺序：

1. 服务页及其入口。
2. 课程前端页面。
3. 课程用户 API、课程后台面板和课程统计。
4. 预约用户页面和预约 API。
5. 咨询师工作台中依赖旧预约的管理部分。
6. 确认旧预约分配对应的历史访问需求，并在需要时补建服务申请分配。
7. 最后再通过新的数据库迁移处理预约、课程相关表及历史数据。

预约应当最后处理，因为后台和咨询师工作台仍提供预约管理能力，且需要保留历史数据供审计与迁移核对。

## 七、最终判断

如果当前目标是稳定推进报告和日历，**可以保留这些代码，但应视为冻结的兼容代码，而不是继续参与当前产品开发的活跃模块**。

如果当前目标是做一个极简、低维护的报告 + 日历 MVP，可以继续保留预约后端、后台以及数据库作为兼容能力。咨询师访问报告和日历的授权替代已完成；彻底清理前仍需确认仅有旧预约分配的历史授权需求、生产数据和外部调用。
