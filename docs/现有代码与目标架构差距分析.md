# 现有代码与目标架构差距分析

> 分析日期：2026-10-03  
> 目标基线：[辰鉴 AI 内容生产工作流与 Skills 架构设计 v1.0](辰鉴_AI内容生产工作流与Skills架构设计_v1.0_最终版.md) 第 64、71–79 节  
> 范围：现有 InnerPath 报告生产、咨询师交付与其相邻领域；本文件是扫描结果和落地顺序建议，不是代码迁移记录。

## 结论摘要

InnerPath 已具备模块化单体、报告生成、咨询师申请与交付、Celery 异步处理、粗粒度草稿历史、审计和基于分配关系的咨询师授权。目标设计不应从零重写这些能力。

当前尚无目标设计的核心生产骨架：Report Case 聚合、不可变 Workflow/Skill 版本、Workflow Instance 与逐 Step Task、Transactional Outbox、Evidence/Finding/Fragment 语义资产、STALE 传播、NarrativePlan、QA Issue、动态 Example，以及不可变 ReportVersion。现有任务、草稿和报告分别覆盖了其中一部分职责，但生命周期和追溯语义不同。

需要保留并明确衔接两条现有报告入口：用户自助报告生成（`POST /reports`）与咨询师服务申请报告生成。后一条更接近目标的人在回路流程；前一条当前绕过 Case、咨询师审核和交付门禁。切换前需把两条入口的产品去留和目标 Workflow 行为定下来，不能通过删旧入口或把不同生命周期硬塞进同一状态字段来隐式解决。

目标与现有业务表恰好都为 14 张，这是数量巧合，不代表等价。推荐在现有模块化单体内增量增加报告生产领域能力，保留共享账户、认证、审计、日历、管理端和任务基础设施；通过兼容层逐步连接现有服务申请和报告读写路径。数据库改动应使用新的前向 Alembic 迁移，不改写已存在迁移。

## 第 77 节：现状问题回答

### 1. 当前 Report / Case 数据模型是什么？

- `reports`（`backend/app/domains/reports/models.py`）保存已生成报告：用户、出生资料、输入快照、结构化报告字段、私有 AI 原文、模型名、审核人/时间和完成/删除状态。它更像报告结果记录，不是整个生产过程的 Case。
- `report_tasks` 保存用户自助生成任务及状态、进度、输入快照和重试关系。
- `service_requests` 表示报告或日历申请，保存申请快照、分配咨询师、工作流状态和交付结果引用；它是当前最接近 Case 的实体，但同时承担报告与日历两种服务，没有 Workflow Version/Instance、当前 NarrativePlan 或语义资产关系。
- `service_request_drafts` 和 `service_request_revisions` 保存咨询师 AI 草稿、可编辑副本及少量阶段快照。
- 报告 Case 目前不存在。两条报告生成路径也没有统一的 Case ID 或生产生命周期。

### 2. 当前 Workflow / 状态流转在哪里实现？

- 咨询师流程主要在 `backend/app/domains/service_requests/{users,staff,workflow,repository}.py` 与 `backend/app/application/service_request_{ai,delivery}.py`。`service_requests.status` 包括 `submitted`、`accepted`、`ai_processing`、`ai_ready`、`reviewing`、`needs_info`、`failed`、`delivered`、`withdrawn`、`rejected`。
- 自助报告流程由 `report_tasks.status` 表示，主要状态是 `processing`、`completed`、`failed`；Celery 任务内部更新粗粒度进度。
- 多步报告生成有固定的代码顺序，但各步没有独立持久化的 Task、激活次数、指派能力、Return/Reopen 或 CompletionGate。目标的 Workflow 状态机尚不存在。

### 3. 当前 AI Prompt / 模型调用在哪里？

- 单步 Prompt 在 `backend/app/domains/reports/generation/report_prompt.py`；调用 DeepSeek 的 HTTP 请求在 `single_step_report.py`。
- 多步 Prompt、解析和组装在 `multi_step_report_prompts.py`、`multi_step_report_parser.py`、`multi_step_report_sections.py`、`multi_step_report.py`；`backend/app/services/ai_service.py` 根据 `USE_MULTISTEP_GENERATION` 选择多步或单步策略。
- 确定性命理基础、日历换算、结构解析和降级报告已有独立实现，适合作为 Tool/Processor 的代码基础。
- 当前没有 ModelGateway、SkillExecutor、可发布的 SkillVersion、统一 ContextBuilder/PromptAssembler，或按 SkillRun 保存的完整输入、Prompt、模型 Trace 和输出记录。模型 HTTP 调用与报告生成实现仍有直接耦合。

### 4. 当前报告草稿与最终版本如何存储？

- 咨询师流程在 `service_request_drafts` 中保存一份当前 `ai_payload` 和一份可编辑的 `editable_payload`；编辑时更新同一行并增加 `content_version`。
- 交付时 `service_request_delivery.py` 从可编辑草稿创建 `reports` 行，再把请求标记为 `delivered`。报告没有 Case 内的版本号、WorkflowVersion/NarrativePlan 引用或冻结的语义来源快照。
- 自助报告生成结束后直接创建 `reports` 记录，不经过咨询师草稿和交付流程。

### 5. 当前是否已经存在 Revision / History？

存在有限的、整份 JSON 快照级历史：

- `service_request_revisions` 有请求版本号、阶段、完整 payload 和创建人；当前用于再次生成前、用户补充信息重提前及交付时留档。
- `service_request_drafts.content_version` 支持编辑冲突检测，但每次普通保存不会形成不可变 Revision。
- 日历另有已发布版本号，用户档案有 `profile_version`。
- 不存在 Finding/Fragment 独立 Revision、Semantic Revision 与 Content Revision 区分、Source Snapshot、依赖图或 STALE 传播。`reports` 也没有不可变 ReportVersion 约束。

### 6. 当前异步任务如何实现？

- 使用 Celery；入口在 `backend/app/tasks/`，运行状态另存于 `report_tasks` 或 `service_request_tasks`，部分进度使用 Redis。
- 直接报告 API 先持久化任务并提交，再写缓存并调用 `apply_async`。服务申请通过 application 注入调度函数，任务入口仍在 `tasks/`。
- 两种任务记录都是整段生成/重试任务，不是目标的 Workflow Instance 或逐步 StepTask。数据库事务与 Broker 投递之间目前没有 Outbox；若任务行提交后投递失败，需要额外恢复手段，数据库本身不能证明任务已送达。
- 目标约束“Celery 是执行器、数据库是 Source of Truth”可沿用现有边界，但需要 Outbox 和幂等消费补齐可靠投递。

### 7. 当前权限 / Capability 如何实现？

- `backend/app/dependencies.py` 提供登录用户和 `user`、`consultant`、`admin` 角色检查；咨询师对服务申请的操作依据分配关系。
- 报告、任务和日历读取的咨询师授权通过有效分配关系判断；被分配给当前咨询师且状态不是 `withdrawn` 或 `rejected` 的申请授予相关读取权。管理员有管理能力。
- 当前没有按 Workflow Step 声明的 Capability，也没有角色到 Capability 的独立映射。目标可先用现有角色/分配规则实现 Capability 适配，不必先改造全部账户授权。

### 8. 当前数据库有哪些表可以复用？

从 ORM 与迁移链整理出的 14 张当前业务表：

| 领域 | 当前表 |
|---|---|
| 账户 | `users` |
| 认证 | `auth_sessions`、`staff_invites` |
| 报告 | `reports`、`report_tasks` |
| 服务申请 | `service_requests`、`service_request_drafts`、`service_request_revisions`、`service_request_tasks` |
| 日历 | `user_calendars`、`calendar_requests`、`calendar_entries`、`decision_logs` |
| 审计 | `audit_logs` |

`008` 已从当前 Schema 删除预约与课程相关表；其历史迁移仍在迁移链中，不表示这些表仍是当前运行模型。新设计应复用账户、审计、日历和现有服务申请事实，但不应把 `reports` 或 `service_request_revisions` 直接当作新版本体系。

### 10. 哪些模块可以保留？

- `backend/app/domains/reports/generation/` 中确定性命理计算、输入归一、解析、降级及现有领域知识；逐步将其注册为 Tool/Processor，不重写算法。
- `backend/app/domains/reports/` 的报告契约、查询和兼容读 API；在新 `report_versions` 落地时由适配层维持现有响应。
- `backend/app/domains/service_requests/` 中仍服务当前用户申请、咨询师分配、日历申请及必要的兼容工作流。它可以作为旧入口和业务边界，报告 Case 完整落地后再评估报告类申请是否迁移/投影。
- `auth`、`users`、`audit`、`calendar`、`admin`、`core`、`db` 与 `tasks` 的既有所有权和模块化单体部署方式。
- 前端报告展示、服务申请 API 与咨询师工作台中的可复用列表/操作；工作台增加步骤和语义审核能力时按领域渐进扩展。

### 11. 哪些模块需要重构？

- **报告生产编排**：把 `ai_service.py` 的策略分派与单步/多步实现纳入 Skill Runtime，但第一版先包装现有生成器，不把 Prompt 和算法一起重写。
- **任务模型**：新增 Workflow Instance/StepTask/Outbox；现有 `report_tasks` 与 `service_request_tasks` 通过兼容适配和逐步切流退出生产编排职责。
- **草稿与修订**：从整份 JSON 草稿演进为 Finding/Fragment 当前版本与历史版本；保留现有草稿格式作为旧 API 适配或迁移输入。
- **交付**：把报告组装、QA 门禁和不可变 ReportVersion 作为新的交付路径；现有 `reports` 在兼容期继续供现有读取端使用。
- **授权**：把当前角色/分配检查映射到 Step 所需 Capability；保留已有访问规则，不在此次改造中扩大咨询师数据可见范围。
- **咨询师工作台**：从整份报告编辑扩展为按当前 Step 查看资料、Evidence、已确认上游语义资产和 Fragment 的流程界面。
- **两条报告入口**：确定自助入口和咨询师申请如何映射到 Case/Workflow，再进行统一；在决策前保留已有 URL 与客户端契约。

### 12. 哪些新增功能可增量接入而无需重写？

- 在现有领域结构内新增 `workflow`、`report_cases`、`content`、`skills`、`authoring`、`quality`、`delivery` 等职责包；HTTP 仍在 `api/v1/`，跨域编排仍在 `application/`，Celery 仍在 `tasks/`。
- 先增加 Case、WorkflowVersion、WorkflowInstance、StepTask 和 Outbox；通过适配器复用当前申请快照、咨询师分配和任务执行器。
- 把现有单步/多步生成器作为首批固定 SkillVersion 的执行实现，再逐步替换其 Prompt 组装和模型调用实现。
- 以当前用户输入、确定性命理基础和申请信息建立 Evidence；随后增加 Finding/Fragment 版本及 StalePropagation，不要求回填全部历史报告。
- 新增 NarrativePlan、Programmatic QA、Validator、QAIssue 与 ReportAssembler；现有报告页面和 API 可先读取兼容投影。
- 在咨询师工作台逐步增加 Finding 审核、Fragment 编辑、Step Complete、Return/Reopen 和最终交付门禁。
- 在最终 QA 与交付稳定后增加 Example 审核发布、Dynamic Retrieval、Skill Evaluation 和 Regression Dataset。

## 第 79 节：适配 InnerPath 的实施顺序

各阶段顺序沿用目标文档的 Phase 1–7；阶段之间通过兼容层渐进切换，不批量搬移稳定模块。

| 阶段 | InnerPath 落地重点 | 阶段验收 |
|---|---|---|
| 1. Workflow 与 Version 基座 | 新增报告 Case、WorkflowVersion/Instance、StepTask、Outbox；实现 Sequential Workflow、激活、CompletionGate、Return/Reopen。先明确报告类服务申请与自助生成的 Case 入口映射。 | 暂不接 AI，纯人工流程可完整提交、推进、退回、重开、完成；发布版本不可原地修改；Outbox 可恢复投递。 |
| 2. Skill Runtime | 新增 SkillVersion、SkillRun、Executor、Context/PromptAssembler、ModelGateway；把当前单步生成包装为首个固定版本 Skill，保存完整输入、版本、Trace 和结构化输出。 | 指定 Step 可用固定 SkillVersion 执行一次结构化生成，重复事件有幂等结果且运行可追踪。 |
| 3. Evidence / Finding / Fragment | 从新 Case 的输入快照和确定性计算结果生成 Evidence；新增 Finding/Fragment Revision、Semantic Edit、Style Edit 与 StalePropagation。 | 修改被依赖的上游 Finding 会使对应下游 Fragment 变为 STALE；纯文案修改不传播。 |
| 4. Consultant Workbench | 在现有咨询师工作台加入 AI Draft、Finding 接受/修改/拒绝/新增、Evidence 查看、Fragment 编辑、Step 完成和退回。 | 咨询师能完成完整专业审核，不需要手工编辑底层 JSON；能力检查与 Case 分配规则一致。 |
| 5. Narrative / Report Authoring | 实现 CaseSemanticModelBuilder、Narrative Candidate/Planner、人工选择、NarrativePlan 和 Report Fragment Authoring。 | 最终写作只依赖确认后的语义资产，不需要重新读取并综合多篇长文。 |
| 6. Final QA / Delivery | 实现程序 QA、Validator Skill、QAIssue、Human Final Gate、ReportAssembler 和不可变 ReportVersion；为现有报告 API 提供读取适配。 | 有 BLOCK 时不能交付；通过 QA 后产生不可覆盖的报告版本，并保留来源快照。 |
| 7. Dynamic Few-shot / Evaluation | 增加 Example Candidate/Publish、脱敏审核、动态检索、Skill Evaluation 和回归样本。 | 优质人工修改可审核后发布为 Example；新 SkillRun 能记录命中的 Example 及版本来源。 |

## 迁移与兼容原则

1. 已有 Alembic 迁移保持不变；新增表和字段使用新的前向迁移。
2. 已交付 `reports` 和既有服务申请历史先保持可读；不把 `service_request_revisions` 伪装成 Finding/Fragment 历史，也不要求无业务收益地回填全部历史内容。
3. 对切换时仍在处理的报告申请和任务，需定义从旧请求/任务到新 Case/WorkflowInstance 的显式关联和恢复策略；历史已交付数据与新版本数据的读取投影也需在 Phase 6 前定稿。
4. 当前咨询师分配授权作为第一版 Capability 适配来源；新步骤按所需能力校验，但不得默认扩大到同一用户的所有历史记录。
5. 日历仍是独立领域。报告交付只调用既有日历边界或后续集成接口，不把日历申请、发布版本和行动记录合并进报告 Case 状态机。
6. 在第一阶段前确定自助报告入口的目标路径：继续提供时，应明确它生成何种 Case/Workflow；若产品决定停止，则需单独安排 API、前端和历史访问的兼容策略。本分析不替产品作此决定。
