# 辰鉴《人生说明书》实际报告生成算法与编排设计 v1.0

> 文档性质：**开发实现文档 / Report Generation Algorithm**
>
> 本文档独立于《辰鉴 AI 内容生产工作流与 Skills 架构设计 v1.0》存在，专门回答：
>
> **“开发端拿到前面确认的分析结果以后，系统究竟应该怎样真实生成一份《人生说明书》？”**
>
> 目标不是描述抽象架构，而是把 **Narrative Planning → 内容分配 → Fragment 生成 → 连贯性控制 → 人工审核 → Final QA** 写成可直接实现的编排算法。
>
> 本文档不负责重新定义 Workflow、Skill、Finding、Fragment 等基础架构；这些概念以主架构文档为准。

---

# 1. 实现目标

禁止把《人生说明书》的生成实现成：

```text
用户资料
+
前四步所有长文
+
一个大 Prompt
↓
LLM
↓
整本报告
```

正式实现必须遵守：

```text
Confirmed Semantic Assets
        ↓
Case Semantic Model
        ↓
Narrative Candidate Generation
        ↓
Human Editorial Choice
        ↓
NarrativePlan
        ↓
Report Content Allocation
        ↓
Fragment-by-Fragment Authoring
        ↓
Local / Chapter / Report Coherence Check
        ↓
Human Editorial Review
        ↓
Final QA
        ↓
ReportAssembler
```

核心目标：

1. 每份报告有自己的叙事主线，而不是固定模板填空；
2. 最终报告只表达已经确认的专业语义，不在写作阶段重新“算”一次；
3. 最终报告每个关键结论可追溯到已确认 Finding / AnalysisFragment；
4. 支持局部重写，不因修改一节而整本重新生成；
5. 避免章节之间反复重复同一个核心判断；
6. 保留整本书的整体阅读感，而不是十几篇独立文章拼接；
7. 能进行稳定 QA；
8. 能持续积累优秀写作案例用于 Dynamic Few-shot。

# 2. 业务依据与系统实现边界

## 2.1 来自现有 SOP 的业务要求

人生说明书最终内容需要完成这样的阅读路径：

```text
看见自己的心灵结构
→ 认识“我是谁”
→ 看见被隐藏或压抑的部分
→ 看见“卡在哪”
→ 理解卡点为什么重复
→ 理解这些模式过去保护了什么
→ 发现几个卡点背后的共同模式
→ 看见真正需要发展的部分
→ 找到人生方向和阶段任务
→ 用行动把新的自己带入现实
```

最终报告整体保持：

```text
你是谁
卡在哪
往哪去
```

但内部小标题、内容顺序、叙事方式和文字风格应根据具体用户变化。

报告写作阶段不能重新进行新的案例诊断或命理推断，核心内容只能建立在已经审核过的前置分析和用户问卷上。

## 2.2 本文档新增的系统实现设计

以下属于系统实现设计，不是原 SOP 的数据结构：

```text
CaseSemanticModel
NarrativeCandidate
NarrativePlan
ReportContentPlan
ReportFragment
SourceMap
PreviousContentSummary
ContentCoverage
Coherence Validator
```

这些概念用于让开发端能够稳定复现 SOP 想要的“形散神不散”。

# 3. 报告生成前置条件

Step 5 Report Authoring 只有在以下条件满足后才能开始：

```text
S1 命理基础分析完成
+
S2 心理映射完成
+
S3 三重整合完成
+
S4 心理机制 / Block / Action 完成
```

同时：

```text
Required AnalysisFragment = CONFIRMED
关键 Finding = CONFIRMED
不存在 Required Fragment 的 STALE
不存在未解决的 BLOCK Guardrail
```

如果不满足：

```text
Report Authoring 不得启动
```

正式 Authoring Context 中允许出现：

```text

HUMAN_CONFIRMED Findings
CONFIRMED AnalysisFragments
Confirmed Block
Confirmed Action
Current NarrativePlan
Authoring Knowledge
```

默认不允许出现：

```text

未确认 Candidate Finding
其他咨询师内部 Chat
```

# 5. 写作阶段的权限

Report Authoring AI 允许：

```text
SELECT
PRIORITIZE
TRANSLATE
ORGANIZE
SYNTHESIZE
EXPRESS
CONNECT
SUMMARIZE
```

禁止：

```text
CREATE_NEW_FACT
CREATE_NEW_DIAGNOSIS
CREATE_NEW_FINDING
CHANGE_FINDING_CONFIDENCE
OVERRIDE_HUMAN_CONFIRMATION
INVENT_USER_EXPERIENCE
INVENT_FUTURE_EVENT
```

如果生成过程中发现必须增加一个新的专业结论才能写通：

```text
不要自行补充
↓
返回 MISSING_SEMANTIC_SUPPORT
```

# 6. 总体算法

完整算法：

```text
INPUT
Confirmed Case Semantic Assets

        ↓

A. BuildCaseSemanticModel

        ↓

B. PrioritizeSemanticAssets

        ↓

C. GenerateNarrativeCandidates

        ↓

D. HumanEditorialChoice

        ↓

E. BuildNarrativePlan

        ↓

F. BuildReportContentPlan

        ↓

G. GenerateReportFragmentsInOrder

        ↓

H. ChapterCoherenceCheck

        ↓

I. ReportCoherenceCheck

        ↓

J. HumanEditorialReview

        ↓

K. FinalQA

        ↓

L. ReportAssembler

        ↓

OUTPUT
Immutable ReportVersion
```

# 7. Stage A：Build Case Semantic Model

`CaseSemanticModel` 是运行时 Projection，不需要数据库表。

从当前 Case 加载：

```text
Evidence
Current CONFIRMED FindingRevision
Current CONFIRMED AnalysisFragmentRevision
Confirmed Block
Confirmed Action
Semantic Relation
User Concern
```

形成：

```json
{
  "facts": {},
  "user_concerns": [],

  "identity": {
    "persona": [],
    "self_belief": [],
    "resources": [],
    "hidden_sides": []
  },

  "dynamics": {
    "central_tension": [],
    "core_complex": [],
    "defense": [],
    "repeated_patterns": [],
    "relationship_cycle": []
  },

  "blocks": [],

  "direction": {
    "self_direction": [],
    "integration_tasks": [],
    "current_stage": [],
    "timing": []
  },

  "actions": []
}
```

注意：

> CaseSemanticModel 不产生任何新结论，只重新组织已经确认的语义资产。

---

# 8. Stage B：Semantic Prioritization

不是所有 Confirmed Finding 都需要写进最终报告。

先做内容优先级计算。

建议优先级来源：

```text
reportability
importance
user concern relevance
block relation
self direction relation
narrative usefulness
```

第一优先级：

```text
reportability = MUST_INCLUDE
```

第二优先级：

```text
importance = CRITICAL / HIGH
```

第三优先级：

```text
与用户明确关注问题直接相关
```

第四优先级：

```text
能够解释多个 Block 的共性 Finding
```

第五优先级：

```text
能够支持 Action / Integration Direction 的 Finding
```

低优先级内容可以保留在 Analysis Space，而不写入最终报告。

---

# 9. Semantic Prioritization 输出

建议形成运行时对象：

```json
{
  "must_include": ["F12", "F31", "F77"],
  "high_priority": ["F18", "F32", "F52"],
  "optional": ["F66", "F67"],
  "internal_only": ["F05", "F09"],

  "candidate_blocks": ["B01", "B02", "B03", "B04", "B05", "B06"],

  "candidate_actions": ["A01", "A02", "A03"]
}
```

# 10. Block 选择算法

最终报告应突出最重要的约 4～5 个 Block。

AI 可以根据以下因素排序：

```text
importance
用户现实痛点相关度
Evidence 强度
是否重复出现
是否可以被多个 Finding 解释
是否与 Self Direction 形成明确对应
是否能够落到可执行 Action
```

AI 给出推荐：

```text
B03 CRITICAL
B01 HIGH
B07 HIGH
B04 HIGH
B09 MEDIUM-HIGH
```

最终由人工允许：

```text
保留
移除
替换
重新排序
```

正式 NarrativePlan 中只保存最终选定结果。

---

# 11. Stage C：Narrative Candidate Generation

Narrative Planner **不写最终正文**。

它只负责回答：

> “对于这个具体用户，整份人生说明书最适合沿着哪条暗线讲？”

一次生成 2～3 个 Narrative Candidate。

每个 Candidate 必须足够不同，不能只是换标题。

---

```json
  "rationale": "为什么这条暗线最能解释当前案例",

  "supporting_findings": [
    "F018",
    "F031",
    "F047"
  ],

  "priority_blocks": [
    "B01",
    "B03",
    "B05",
    "B07"
  ],

  "self_direction": "F077",

  "user_concern_coverage": [
    "career_choice",

  ],

  "deemphasized_findings": [
    "F061"
  ],

  "narrative_arc": [
    "先让用户认出自己习惯呈现给世界的样子",
    "进入这种表现背后的内在压力",

    "说明真正需要整合的是哪两个对立面",
    "把新的理解带到未来阶段和现实行动"
  ]
}
```

---

# 13. Candidate 之间必须体现真实差异

例如同一个 Case：

```text
Candidate A
外部评价 → 内部主权
```

```text
Candidate B
通过承担责任换取稳定
→ 学会让真实需要进入关系
```

```text
Candidate C
过度准备 → 在不确定中行动
```

三者可以都成立，但强调重点不同。

这正是 Human Editorial Choice 存在的意义。

---

# 14. Stage D：Human Editorial Choice

人工不从零设计 Narrative Plan。

只做高价值选择：

```text
选择哪一个 Narrative Candidate
确认 / 调整核心主题
确认 / 调整主暗线
确认 4～5 个核心 Block
确认核心 Self Direction
确认用户最关心的问题有没有被覆盖
```

人工不需要在此阶段：

```text
逐段写正文
重新分析命盘
重新产生心理 Finding
```

# 16. Reader Profile

Reader Profile 只影响表达，不得改变事实和核心语义。

可控制：

```text
directness
warmth
theory_density
action_density
length
metaphor_density
```

例如：

```json
{
  "directness": "high",
  "warmth": "medium",
  "theory_density": "low",
  "action_density": "high",
  "metaphor_density": "low"
}
```

注意：

> MBTI / 八维只允许在有用户自报时作为明确锚点；没有自报时不得反推具体 MBTI 类型。

# 17. Stage F：Report Content Allocation

这是实际报告生成最关键的一步之一。

NarrativePlan 确认后，**不能立刻开始写正文**。

必须先形成：

> `ReportContentPlan`

作用：

> 明确“哪些 Finding / Block / Action 应该在哪个 Fragment 中承担什么职责”。

`ReportContentPlan` 可以作为 NarrativePlan 内部 JSON，也可以作为运行时对象，不需要独立数据库表。

---

# 18. 为什么必须 Content Allocation

如果没有这一步，每个 Fragment 都独立从 CaseSemanticModel 中选信息，很容易出现：

```text
同一个核心 Finding
↓
你是谁 写一次
↓
卡点1 再写一次
↓
卡点共性 再写一次
↓
往哪去 又写一次
```

最后产生：

> 每一段都对，但整本报告非常重复。

Content Allocation 的目标就是提前规划：

```text
某个 Finding 在哪里第一次完整展开
在哪里只做引用
在哪里只做回应
哪里禁止重复解释
```

---

# 19. ReportContentPlan Schema

```json
{
  "fragments": [
    {
      "fragment_key": "report.identity.outer_self",

      "purpose": "建立用户的识别感",

      "primary_findings": ["F012", "F018"],

      "supporting_findings": ["F021"],

      "blocks": [],

        "用户熟悉的外在表现"

      "supporting_findings": ["F018"],

      "must_not_repeat": [
        "不要重新完整解释 F018"
      ],

      "new_information_role": "DEEPEN"
    }
  ]
}
```

# 20. Finding 在报告中的表达角色

一个 Finding 在不同 Fragment 中的使用应有角色：

```text
INTRODUCE
DEEPEN
MANIFEST
SYNTHESIZE
RESPOND
REFERENCE
```

例如：

```text
F018 外部评价敏感
```

可以：

```text
你是谁：INTRODUCE
卡点1：MANIFEST
共性模式：SYNTHESIZE
往哪去：RESPOND
```

这和四次完整重复解释完全不同。

# 22. 第一章：你是谁

核心任务：

> 从用户已经容易认出的自己出发，逐步进入更深层的心理结构。

推荐顺序：

```text
整体心灵结构
↓
世界看到的你
↓
你眼中的自己
↓
被隐藏的自己
↓
能量运作
↓
关系模式
↓
Self Direction 的预埋
```

本章重点：

```text
IDENTITY
PERSONA
RESOURCE
SHADOW
RELATIONSHIP
CENTRAL TENSION
```

本章不应该：

```text
把所有 Block 全部展开
大量给解决方案
提前进入完整行动计划
```

---

# 23. 第二章：卡在哪

先选择最终最重要的 4～5 个 Block。

每个 Block Fragment 应至少回答：

```text
常见现实场景
↓
这个模式如何运作
↓
什么会触发它
↓
它过去保护了什么
↓
长期代价是什么
↓
它在邀请用户看见什么
```

Block 不应只是：

> “你有 XX 问题。”

而应该呈现：

```text
现实体验
→ 内在机制
→ 保护功能
→ 长期代价
→ 更深层需要
```

# 25. 卡点共性模式

`report.blocks.common_pattern`

不是再写第六个 Block。

它必须回答：

> “前面 4～5 个看似不同的问题，背后是不是同一套系统在运作？”

例如：

```text
外部评价敏感
↓
先提高标准
↓
过度准备
↓
不敢暴露不确定
↓
延迟行动
↓
再次需要证明自己
```

应该尽量以：

```text
Pattern Chain
```

形式表达。

---

# 26. 破局点

`report.blocks.breakthrough`

不是泛泛给建议。

它需要沿着：

```text
Confirmed Block
↓
共性模式
↓
核心 Self Direction
↓
需要发展的心理能力
↓
现实中缺少的能力
↓
匹配 Action / 心理学工具
```

形成。

核心问题：

> “真正要突破的，不是五个表面问题，而是哪一个更底层的能力？”

---

# 27. 第三章：往哪去

核心职责：

```text
解释当前阶段
↓
说明可能被放大的主题
↓
明确发展方向
↓
把方向转成现实行动
```

时序内容必须采用：

```text
阶段主题
触发窗口
可能被放大的议题
适合发展的能力
需要留意的旧模式
```

不得实现成：

```text
确定未来事件预测
```

---

# 28. Growth Experiment

每个成长实验应至少能回答：

```text
它回应哪个 Block？
要发展什么心理能力？
具体怎么做？
频率如何？
用户观察什么？
为什么这个实验适合这个人？
```

结构：

```json
{
  "name": "...",
  "target_block": "B03",
  "target_capability": "...",
  "framework": "CBT",
  "instruction": "...",
  "frequency": "weekly",
  "difficulty": "low",
  "why_it_matches": "...",
  "expected_observation": "..."
}
```

禁止生成和前面案例没有关系的“通用心理建议套餐”。

---

# 29. Stage G：Fragment Generation Order

ReportFragment 不建议完全并行。

推荐：

```text
Chapter 1
顺序生成

        ↓

Chapter 2
Block 之间可以受控并行
Common Pattern 必须在 Blocks 后生成
Breakthrough 必须在 Common Pattern 后生成

        ↓

Chapter 3
顺序生成

        ↓

Ending
最后生成
```

具体：

```text
overview
↓
identity.outer_self
↓
identity.self_perception
↓
identity.hidden_self
↓
identity.energy_pattern
↓
identity.relationship_pattern
↓
identity.self_direction

↓

// 4～5 Block 可以有限并行
block_01
block_02
block_03
block_04
block_05

↓
common_pattern
↓
breakthrough

↓
current_stage
↓
life_map
↓
growth_experiments

↓
ending
```

---

# 30. 为什么不能全部并行

十几个 Fragment 全并行会导致：

```text
不知道前面已经写过什么
↓
重复解释
↓
隐喻重复
↓
不同章节对同一个 Finding 的表达不一致
↓
整本报告像独立文章拼接
```

因此必须有：

```text
Local Continuity Context
```

# 31. Previous Content Summary

生成当前 Fragment 时，不把之前全文全部传进去。

而是由系统维护：

```json
{
  "previous_content_summary": {
    "established_points": [
      "已经向用户介绍 F018",
      "已经说明外在评价与自我要求的关系"
    ],

    "used_metaphors": [
      "内部评委"
    ],

    "used_findings": [
      "F018",
      "F021"
    ],

    "unresolved_threads": [
      "还没有解释这种模式如何进入关系"
    ],

    "avoid_repeating": [
      "不要重新完整介绍 F018"
    ]
  }
}
```

这样既保持连贯，又避免 Context 无限增长。

# 35. Dynamic Few-shot 的使用方式

Authoring Example 必须按 Fragment 类型检索。

例如：

```text
report.identity.hidden_self
```

只检索：

```text
hidden_self 类优秀写作案例
```

而不是从所有人生说明书中随机 TopK。

推荐：

```text
same skill
+
same fragment type
+
scenario tags
+
style compatibility
+
semantic pattern similarity
↓
Top 2~3
```

Example 只教：

```text
怎么表达
怎么组织
怎么过渡
```

不能把 Example 中的用户事实迁移到当前用户。

# 36. Chapter Coherence Check

每完成一章，执行一次 Chapter Validator。

第一章检查：

```text
是否从意识层逐渐深入
是否提前进入过多 Block
是否重复介绍同一 Finding
是否过多暴露命理分析框架
是否出现强人格定论
```

第二章检查：

```text
Block 是否真正不同
Block 是否存在高度重叠
共性模式是否真的总结前面 Block
Breakthrough 是否回应共性模式
是否每个 Block 都提前重复给完整方案
```

第三章检查：

```text
阶段方向是否回应前面问题
行动是否来自 Block / Self Direction
是否出现确定性未来
是否变成通用鸡汤
```

# 37. Chapter Validator 不允许整体重写

输出：

```json
{
  "issues": [
    {
      "type": "REPETITION",
      "severity": "WARN",
      "target_fragment": "report.blocks.block_03",
      "message": "..."
    }
  ]
}
```

由：

```text

```

局部修正。

禁止：

```text
把整章交给模型重新写一遍
```

# 38. Report-level Coherence Check

所有 Fragment 生成完成后执行。

检查：

```text
核心暗线是否贯穿
NarrativePlan 是否真正落实
MUST_INCLUDE Finding 是否覆盖
用户核心问题是否被回应
是否存在章节前后冲突
是否存在 Finding 过度重复
是否有核心 Finding 完全遗漏
Action 是否回应 Block
第三章是否回应第二章
开头与结尾是否呼应
```

# 39. Coverage Matrix

动态生成：

| Semantic Asset | 使用位置 | Role | 状态 |
|---|---|---|---|
| F018 | outer_self / block_01 / breakthrough | INTRODUCE / MANIFEST / RESPOND | 正常 |
| F031 | hidden_self / common_pattern | INTRODUCE / SYNTHESIZE | 正常 |
| F077 | self_direction / growth_experiment | INTRODUCE / RESPOND | 正常 |

候选问题。

# 41. Semantic Gap

如果当前 Fragment 根据分配内容无法合理完成：

```text
MISSING_SEMANTIC_SUPPORT
```

示例：

```json
{
  "type": "MISSING_SEMANTIC_SUPPORT",
  "target_fragment": "report.identity.relationship_pattern",
  "needed": "关系模式的核心需求缺少已确认 Finding",
  "related_sources": ["F031"]
}
```

处理：

```text
创建 Issue
↓
人工决定是否 Reopen 对应 Analysis Step
↓
新增 / 修改 Finding
↓
相关下游 STALE
↓
重新生成相关 Fragment
```

Authoring AI 绝不能自行补一个新的心理结论。

# 42. 局部 Regenerate

每个 ReportFragment 都支持局部重生成。

输入：

```text
当前 Fragment
+
NarrativePlan
+
Current Content Allocation
+
当前 Confirmed Sources
+
用户指定 Rewrite Instruction
+
QA Issue（如果有）
```

输出新的：

```text
FragmentRevision
```

不会覆盖旧 Revision。

---

# 43. Rewrite Instruction 边界

允许：

```text
更直接
更温和
减少理论词
增加现实感
压缩篇幅
增加一个隐喻
降低确定性
加强与前文衔接
减少重复
```

不能：

```text
“换一个心理结论”
“再猜猜用户为什么这样”
“补一个新的家庭创伤经历”
```

涉及语义变化必须回到 Analysis Space。

---

# 44. 人工直接改正文

如果人工修改：

```text
只改变表达
→ STYLE_EDIT
```

如果人工改变：

```text
核心判断
→ SEMANTIC_EDIT
```

Report Space 原则上不鼓励产生独立于 Analysis Space 的 Semantic Edit。

如果人工想把：

> “核心原因 A”

直接改成：

> “核心原因 B”

系统应提示：

```text
这属于语义变化，请同步修改上游 Finding。
```

# 45. Human Editorial Review

Step 5 人工终审主要检查：

```text
这份报告像不像这个用户
NarrativePlan 是否真的成立
重点是否选对
文章是否容易读
是否出现大量模板感
关键 Block 是否表达清楚
Action 是否足够现实
整体风格是否符合产品
```

这里不要求重新做 S1～S4 的专业分析。

---

# 46. Step 5 Completion Gate

必须满足：

```text
NarrativePlan = CONFIRMED

Required ReportFragments 全部存在

所有 Required ReportFragments = CONFIRMED

所有 source findings = CONFIRMED

不存在 SOURCE_STALE

不存在 NARRATIVE_STALE

不存在 unresolved semantic gap

不存在 authoring BLOCK

人工 Editorial Review 完成
```

才允许进入 Final QA。

# 47. Final QA 编排

固定顺序：

```text

↓

PASS
↓
LLM Semantic QA
↓

↓

↓
```

# 48. Programmatic QA

程序优先检查：

```text

Fragment 是否 STALE

Source Revision 是否一致
NarrativePlan 是否最新
MUST_INCLUDE Finding Coverage

Block → Action Coverage

明确禁用词规则
```

明显结构错误不要浪费 LLM Token。

# 49. LLM Semantic QA

检查：

```text
事实忠实度
Semantic Consistency
虚构用户经历
单信号强推人格
心理诊断 / 人格障碍诊断
确定性未来
把命理表达成科学诊断
章节越界
过度重复
个性化不足
行动与案例脱节
核心暗线断裂
```

Validator 只输出 Issue，不自动改完整报告。


调用：

```text

```

而不是：


# 52. ReportAssembler

```text

↓

↓

↓
```

# 53. 严禁 Final Whole-report Rewrite

这是开发必须遵守的硬约束。

禁止：

```text
全部 ReportFragment
↓
LLM：“帮我统一润色成完整文章”
↓
最终报告
```

原因：

```text
SourceMap 被破坏
已审核语义可能被改写
可能产生新结论
可能产生新事实
局部版本追踪失效
QA 结果失效
```

正确方式：

```text
全局检查
↓
发现具体 Issue
↓
局部 Fragment 修复
↓
重新检查
```

# 54. Fragment 之间的过渡

避免每节像独立文章。


# 55. 小标题生成

小标题属于 Presentation。

可以由 AI 动态生成。

约束：

```text
能概括本节核心
避免模板化
避免玄学式神秘标题
避免夸张和绝对化
不要泄露内部技术术语
```

同一报告的小标题风格应保持一致。

# 56. 命理语言到用户语言

最终报告不应机械输出：

```text
印旺为忌
伤官见官
福德宫化忌
```

而应通过 Authoring Skill 转为用户可理解的：

```text
心理运作
现实体验
内在张力
阶段主题
```

必要时命理概念可以作为：

```text
辅助说明
```

但不能成为用户理解报告的前提。

---

# 57. 描述强度

根据 Finding confidence 调整措辞。

例如：

```text
HIGH
→ “你往往……”
```

```text
MEDIUM
→ “你可能更容易……”
```

```text
LOW
→ 原则上不作为核心用户结论；
如必须出现，应采用更强保留表达
```

禁止低置信 Finding 被写成：

```text
“你就是……”
```

---

# 58. 用户 Evidence 的优先级

如果：

```text
AI 推断
```

与：

```text
用户明确自述
```

存在冲突：

不要偷偷选择 AI。

正确：

```text
保留冲突
↓
交由人工分析
```

最终报告可以在适当情况下表达：

> “这里存在一个值得继续观察的张力……”

而不是强行输出唯一答案。

# 59. 风格控制

最终用户内容：

```text
第二人称“你”
清晰
有心理洞察
有画面
容易理解
不过分学术
不过度煽情
```

避免：

```text
连续安慰
大量空泛金句
故作神秘
过度宿命
过量术语
反复“你不是……你只是……”
```

# 63. Orchestrator 伪代码

```python
def generate_life_manual(case_id):
    assert analysis_ready(case_id)

    semantic_model = build_case_semantic_model(case_id)

    priority = prioritize_semantics(semantic_model)

    candidates = run_narrative_planner(
        semantic_model=semantic_model,
        priority=priority,
    )

    narrative_plan = wait_for_human_editorial_choice(candidates)

    content_plan = build_report_content_plan(
        semantic_model=semantic_model,
        narrative_plan=narrative_plan,
    )

    continuity = empty_continuity_state()

    for fragment_spec in generation_sequence(content_plan):

        context = build_authoring_context(
            case_id=case_id,
            narrative_plan=narrative_plan,
            fragment_spec=fragment_spec,
            continuity=continuity,
        )

        fragment = run_authoring_skill(context)

        validate_no_new_semantics(fragment)

        save_fragment_revision(fragment)

        continuity = update_continuity_state(
            continuity,
            fragment,
        )

    chapter_issues = run_chapter_validators(case_id)

    resolve_required_issues(chapter_issues)

    report_issues = run_report_coherence_validator(case_id)

    resolve_required_issues(report_issues)

    wait_for_human_editorial_review(case_id)

    run_final_qa(case_id)

    wait_for_human_final_gate(case_id)

    return assemble_immutable_report_version(case_id)
```

# 64. Authoring Context Builder 伪代码

```python
def build_authoring_context(

    narrative_plan,
    fragment_spec,
    continuity,
```

```text
hidden_self
block_01
common_pattern
breakthrough
growth_experiments

+
Final QA
```

验证：

```text
Semantic → Narrative → Fragment → QA
```

这条核心链成立后，再扩展成完整报告。

# 76. 完整验收场景

给定一个已经完成 S1～S4 的 Case。

系统必须能够：

1. 构建 CaseSemanticModel；
2. 找出重要 Finding；
3. 推荐 4～5 个 Block；
4. 生成至少 2 条不同 Narrative Candidate；
5. 人工选定一条；
6. 生成 NarrativePlan；
7. 自动生成 ReportContentPlan；
8. 明确每个 Fragment 的 Source；
9. 按规划顺序生成 ReportFragment；
10. 不重复完整解释同一 Finding；
11. 能够从第一章自然承接到第二章；
12. 共性模式真正总结多个 Block；
13. Breakthrough 真正回应共性模式；
14. Growth Experiment 真正对应 Block / Self Direction；
15. 全文无新增无依据事实；
16. 全文无确定性未来；
17. QA 可以定位问题到具体 Fragment；
18. 修改一个 Finding 后，只让受影响 Fragment STALE；
19. 局部重新生成后可重新通过 QA；
20. 最终通过 ReportAssembler 生成不可变 ReportVersion。

# 77. 验收失败示例

以下任一情况均视为实现不合格：

```text
每份报告虽然章节不同，但正文高度模板化
```

```text
同一个核心观点在多个章节重复完整解释
```

```text
某个 Fragment 写出了不存在于 Confirmed Finding 中的新心理判断
```

```text
AI 编造了用户童年、家庭、亲密关系具体经历
```

```text
Block 与 Action 没有关系
```

```text
往哪去变成与前文无关的通用励志内容
```

```text
NarrativePlan 改了，系统却不知道哪些 Fragment 需要重审
```

```text
最后通过整篇 AI 润色破坏 SourceMap
```

# 78. 对开发端最重要的一句话

人生说明书的生成不是：

> **“让模型写一篇好文章。”**

而是：

> **“把已经审核过的案例语义资产，先设计成一条属于这个人的叙事，再有计划地分配到不同内容单元中，逐步写出、局部审核、全局校验，最终形成一份完整且可追溯的报告。”**

系统真正要实现的是：

```text
Semantic Truth
        ↓
Narrative Choice
        ↓
Content Allocation
        ↓
Controlled Authoring
        ↓
Coherence
        ↓
Quality Gate
```

而不仅仅是 Prompt Engineering。
